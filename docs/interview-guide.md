# راهنمای توضیح و دموی پروژه

این راهنما برای آماده‌شدن داوطلب است. برنامه با Mock سروری ساخته شده است؛ برای استفاده از demo و پاسخ‌های زیر، نتیجه واقعی هر بررسی را در [گزارش بررسی](verification.md) ببینید و کد را شخصاً مرور کنید. توضیح را با کد و شاهد همان نسخه تطبیق دهید و نتیجه‌ای را که ندیده‌اید، به‌عنوان تجربه اجرا بیان نکنید.

## معرفی کوتاه

متن زیر را پس از تکمیل و با بیان خودتان استفاده کنید:

> مسیر هتل را انتخاب کردم تا یک جریان جست‌وجوی کامل را با کیفیت پیاده‌سازی کنم. تمرکز من روی قرارداد تاریخ و URL، جداسازی منطق دامنه از UI و مدیریت حالت‌های سرویس بود. داده‌ها Mock هستند، اما ورودی جست‌وجو، فیلتر و مرتب‌سازی و مبلغ اقامت واقعاً محاسبه می‌شوند. معماری یک مرز provider دارد تا تغییر تأمین‌کننده به تغییر کامپوننت‌ها وابسته نباشد.

اگر بخشی کامل نشده، همان بخش و اثرش را روشن بگویید. پاسخ دقیق به یک محدودیت، از ادعای کلی «Production-ready» قابل دفاع‌تر است.

## مسیر دموی پنج تا هفت دقیقه‌ای

| زمان | اقدام پس از ساخت | چیزی که به ارزیاب نشان می‌دهد |
| --- | --- | --- |
| ۰ تا ۱ دقیقه | هدف، محدوده هتل و وضعیت واقعی اجرا را توضیح دهید. | فهم مسئله و کنترل دامنه |
| ۱ تا ۲ دقیقه | شهر تهران و اقامت دوشبه آینده را با تقویم شمسی ثبت کنید. | فرم، محدودیت تاریخ، Loading و قرارداد date-only |
| ۲ تا ۳ دقیقه | بازه قیمت و ستاره را اعمال و sort را عوض کنید. | محاسبه واقعی و حفظ وضعیت جست‌وجو |
| ۳ تا ۴ دقیقه | URL را Refresh و سپس Back/Forward کنید. | بازیابی مستقل از حافظه و state محلی |
| ۴ تا ۵ دقیقه | جزئیات و پیش‌نمایش را باز کنید؛ نرخ هر شب و کل اقامت را توضیح دهید. | پایان جریان و صحت واحد پول |
| ۵ تا ۶ دقیقه | اصفهان بدون fixture و سپس سرور محلی با سناریوی error را نشان دهید. | تفاوت empty/error و رفتار retry |
| ۶ تا ۷ دقیقه | نمودار معماری و یک تست تاریخ یا URL با خروجی واقعی را باز کنید. | تصمیم فنی و شواهد قابل بررسی |

برای نمایش error از تنظیمات [Mock](contracts.md) استفاده کنید و از قبل سرور سناریوی جدا یا زمان راه‌اندازی دوباره را در نظر بگیرید. وجود خطای ثابت یعنی retry هم دوباره خطا می‌دهد؛ موفقیت تصادفی نمایش ندهید. روی تاریخ ثابت نمونه مستندات دمو نکنید؛ تاریخ آینده از امروز تهران انتخاب شود.

اگر فقط سه دقیقه زمان داشتید، فرم و تقویم، فیلتر و URL، سپس جزئیات و یک تصمیم معماری را نشان دهید. محدودیت‌ها در پایان با جمله‌ای مشخص بیان شوند.

## پرسش‌های محتمل و نکته پاسخ

| سؤال | نکته قابل دفاع و چیزی که باید در کد نشان دهید |
| --- | --- |
| چرا چنین ساختاری انتخاب کردید؟ | مسئولیت app، Feature و provider را در [معماری](architecture.md) توضیح دهید؛ یک import واقعی و یک تابع دامنه بدون React نشان دهید. |
| چرا Clean Architecture رسمی و چند لایه عمومی نساختید؟ | حجم یک Feature و زمان تسک، هزینه لایه‌های عمومی را توجیه نمی‌کرد. مرز دامنه و ورودی/خروجی حفظ شده؛ تعداد پوشه‌ها معیار کیفیت نیست. |
| چرا همه صفحه Client نیست؟ | بخش نیازمند تعامل را در کد مشخص کنید؛ دریافت داده و secret روی سرور می‌ماند و کارت غیرتعاملی به state کلاینت نیاز ندارد. |
| چرا Redux یا React Query ندارید؟ | state ثبت‌شده در URL، داده در سرور و draft در فرم است. اگر بعداً polling یا cache تعاملی لازم شود، تصمیم دوباره بررسی می‌شود. |
| کدام بخش URL را معتبر می‌داند؟ | parser مشترک و schema سرور را نشان دهید؛ URL ورودی غیرقابل اعتماد است و کلاینت تنها مرجع اعتبار نیست. |
| مشکل تاریخ را چطور حل کردید؟ | تقویم دقیق انتخاب‌شده، تبدیل اجزای روز به Gregorian و عدم عبور روز اقامت از timestamp را توضیح دهید. تست نوروز و timezone اجراشده را باز کنید. |
| چرا متن تاریخ را جدا از مقدار فرم نگه می‌دارید؟ | متن ناقص یک draft نمایشی است؛ مقدار فرم در هر تغییر معتبر یا خالی می‌شود تا Enter تاریخ قدیمی را ارسال نکند. تقویم هر دو متن را به‌روز می‌کند. سازگاری خروج پس از پایان ویرایش ورود بررسی می‌شود تا تایپ موقت، خروج معتبر را پاک نکند. تست‌های واقعی SearchForm را نشان دهید. |
| persian و jalali یکسان‌اند؟ | قرارداد این نسخه ماژول persian است. اختلاف احتمالی مستند کتابخانه را بیان کنید؛ صحت همه الگوریتم‌ها را تعمیم ندهید. |
| چطور provider دیگری اضافه می‌شود؟ | interface و composition سروری را نشان دهید؛ mapping و خطاهای آداپتور جدید تغییر می‌کنند و UI قرارداد مشترک را نگه می‌دارد. |
| Mock چه چیزی را ثابت می‌کند؟ | معماری سرویس و رفتار جریان را می‌توان سنجید؛ داده بازار، رزرو واقعی و timeout شبکه از آن نتیجه نمی‌شوند. |
| سیاست Cache چیست؟ | رفتار Mock را از fetch خارجی جدا کنید؛ نسخه نصب‌شده، no-store برنامه‌ریزی‌شده و نتیجه بررسی production واقعی را توضیح دهید. |
| مبلغ و ظرفیت چگونه محاسبه می‌شود؟ | واحد ریال، نمایش تومان، نرخ یک اتاق در هر شب و فرمول مجموع را نشان دهید؛ محدودیت ظرفیت ساده Mock را بیان کنید. |
| چه چیزهایی را تست کردید؟ | تست‌های واقعاً اجراشده و خطری که هر کدام می‌پوشانند را نام ببرید. تست تاریخ، URL و دو sort شاهدهای مناسب‌اند. |
| اگر زمان بیشتری داشتید چه می‌کردید؟ | بر اساس [محدودیت‌ها](decisions.md)، provider واقعی، تازگی قیمت و موجودی، مدل ظرفیت دقیق و بررسی تقویم با صفحه‌خوان را اولویت دهید. |
| چقدر از AI استفاده کردید؟ | کارهای واقعاً واگذارشده و روش مرور خود را دقیق توضیح دهید. یکی از تصمیم‌ها یا اصلاح‌های واقعی خودتان را با diff نشان دهید؛ نقش ساختگی نسازید. |

## چک‌لیست آمادگی شخصی

- بتوانید مسیر داده یک درخواست را از URL تا سرویس و کارت، بدون تکیه به متن حفظ‌شده توضیح دهید.
- بتوانید یک ورودی تاریخ نامعتبر و یک خطای سرویس را بازتولید و تفاوت آن‌ها را نشان دهید.
- زوج‌های تبدیل تاریخ و معنای واحد قیمت را بفهمید و با تست واقعی توضیح دهید.
- برای دو تصمیم، گزینه جایگزین و هزینه انتخاب فعلی را از [تصمیم‌ها](decisions.md) به زبان خود بیان کنید.
- دستور اجرای محلی، نسخه بررسی‌شده، نتیجه تست و محدودیت باقی‌مانده را در دسترس داشته باشید.
- فقط از تصاویر، لینک‌ها و خروجی‌هایی استفاده کنید که به نسخه واقعی تحویل تعلق دارند.

این اسناد باید فهم و قضاوت مهندسی شما را قابل مشاهده کنند. رتبه یا نتیجه استخدام قابل تضمین نیست؛ کیفیت جریان کامل، توضیح روشن تصمیم‌ها و شواهد واقعی قابل ارزیابی‌اند.
